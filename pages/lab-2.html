Race Condition

Learn how overlapping operations can redeem a single-use coupon more than once, then compare vulnerable and fixed behavior.

CWE-362 Concurrency Security Interactive Lab 02

01. The Vulnerability

A Race Condition occurs when the result depends on the order in which concurrent operations execute. This lab uses coupon SAVE50, which has a usage limit of 1.

In Vulnerable mode, both requests can read the coupon as available before either marks it as used. In Fixed mode, the coupon is reserved before waiting.

03. Why It Matters

Race Conditions can cause duplicate coupon redemptions, inconsistent balances, oversold inventory, and other unauthorized operations when concurrent requests access the same shared resource.

04. The Fix

In Fixed mode, the code reserves the coupon before the first asynchronous wait. A second request then sees the coupon as used and is rejected. This example isolates the fixed behavior from the teammate's original applyCoupon() function.

Fixed Implementation (browser simulation) Fixed 
async function applyCoupon(requestId) {
  logEvent(`${requestId} → Checking coupon`);

  if (couponUsed) {
    logEvent(`${requestId} → Rejected`);
    return `${requestId}: Rejected`;
  }

  logEvent(`${requestId} → Coupon available`);

  // FIX: Reserve before any asynchronous waiting.
  couponUsed = true;
  logEvent(`${requestId} → Coupon reserved`);

  logEvent(`${requestId} → Waiting...`);
  await delay(100);

  logEvent(`${requestId} → Accepted`);
  return `${requestId}: Accepted`;
}

Security Improvement: Reserving the coupon before yielding execution prevents duplicate redemption in this browser simulation. Real applications must enforce the usage limit on the server with an atomic update, appropriate locking, or a transaction.
